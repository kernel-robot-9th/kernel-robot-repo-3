# 녹화 프레임·저장 워커·교체 로봇팔 점검

점검일: 2026-10-20. 모터 SDK의 읽기 요청만 사용했다. 모터 설정 쓰기·토크 활성화·로봇 이동·새 시연 녹화는 실행하지 않았다. 기존 데이터와 메타데이터를 수정하거나 삭제하지 않았다.

## 결론

- 기존 왼쪽 v1은 66에피소드·37,012행이며 관절 데이터의 에피소드별 길이·인덱스·유한값 검사를 통과했다.
- 그중 4개 에피소드는 두 카메라 모두 관절 행 수보다 영상 구간이 길다. 긴 꼬리 구간에 이전 동작으로 보이는 불연속 장면이 있다. 중단 후 이미지가 남은 가설과 맞지만 당시 로그가 없어 원인은 확정하지 못한다.
- 설치된 학습 로더는 `영상 시작 시각 + 관절 timestamp`로 읽고 에피소드 범위로 인덱스를 제한한다. 따라서 추가 꼬리가 존재한다는 사실만으로 그 꼬리를 모두 학습했다거나 66개 전체가 망가졌다고 판단할 수 없다.
- 저장 워커의 당시 실제 설정과 녹화 벽시계 시간이 저장 파일에 없어, 워커가 실측 FPS 저하의 원인인지는 확정하지 못한다. 새 녹화는 명시한 워커 설정·실행 로그·30초 타이머 시험으로 확인한다.
- 교체한 두 팔은 정상 읽기 통신됐고 현재 모터 오류는 모두 0이다. 새 USB 일련번호로 고정 경로를 갱신했다. 현재 왼쪽 v2 데이터는 아직 생성되지 않았다.

## 왼쪽 v1에서 추가 영상 프레임이 있는 구간

아래 수량은 카메라 한 대 기준이며 front·wrist에서 동일하게 나타났다.

| episode_index / 실제 순서 | 관절 데이터 프레임 | 메타데이터 영상 구간 프레임 | 추가 꼬리 |
| --- | --- | --- | --- |
| 0 / 1번째 | 563 | 830 | +267 |
| 22 / 23번째 | 565 | 718 | +153 |
| 36 / 37번째 | 538 | 709 | +171 |
| 38 / 39번째 | 492 | 499 | +7 |

카메라별 합계 598프레임, 두 카메라 합계 1,196프레임이 관절 행 수보다 많았다. 나머지 62에피소드의 영상 구간 길이는 관절 행 수와 일치했다. 영상 구간 사이의 시작·끝 연결과 파일 길이는 검사한 메타데이터 범위 내에서 일치했다.

설치본 `LeRobotDataset.add_frame()`은 timestamp를 기본적으로 `frame_index / fps`로 만든다. `_query_videos()`는 에피소드 `from_timestamp`를 더해 조회하고, `_get_query_indices()`는 데이터 에피소드 범위를 벗어나지 않게 제한한다. 관절 길이가 563프레임인 경우 일반 조회는 해당 영상 구간의 첫 563프레임을 대상으로 하므로, 뒤의 추가 267프레임을 자동으로 전부 사용하지 않는다. 첫 유효 구간이 실제 시연과 올바르게 대응하는지까지 완전 증명한 것은 아니다.

영상 인코더는 디렉터리에 존재하는 모든 `frame-XXXXXX.png`를 번호순으로 인코딩한다. 중단된 에피소드에 긴 시도의 PNG가 남고 재개 시 짧은 시도가 같은 번호로 덮어쓰면 뒤쪽 PNG가 남을 수 있다. 이는 코드와 현재 영상의 추가 꼬리를 설명하는 가능한 경로다. 정상 `clear_episode_buffer()`는 이미지 워커 완료를 기다린 뒤 삭제하므로, 워커 개수 자체 때문에 프레임 순서가 섞인다고 단정할 수 없다.

새 [재녹화 명령](LEFT_RERECORD.md)은 별도 v2를 만들고, 중단 후 재개할 때 저장되지 않은 다음 에피소드의 잔여 PNG만 정리하도록 했다. 기존 v1을 수정하지 않는다.

## 저장 워커와 FPS

설치본 기본값은 `num_image_writer_processes=0`, `num_image_writer_threads_per_camera=4`다. 카메라 2대에서는 이미지 저장 스레드 총 8개다. 워커는 PNG 저장을 병렬 처리하며, 목표 `dataset.fps`나 프레임 번호를 바꾸지 않는다. 너무 많은 워커의 CPU 경합이나 저장 지연이 제어 루프 성능에 영향을 줄 수 있으나, 단순히 숫자가 클수록 좋다는 관계는 아니다.

기존 문서 명령은 워커 수를 따로 지정하지 않아 기본값을 사용하는 형태였다. 당시 모든 실행이 그 명령과 같았는지는 로그가 없어 확인하지 못한다. 비스트리밍 모드에서는 `save_episode()`가 워커 완료를 기다린 뒤 에피소드 영상을 인코딩한다. 이 인코딩 대기는 준비·저장 시간에 영향을 주며, 그 자체를 녹화 중 프레임 누락으로 세지 않는다.

최근 8만 모델 3개 평가의 저장 프레임은 564·583·577개다. 세 번 모두 실제 30초 타이머 종료였다면 약 18.8·19.4·19.2FPS였다는 뜻이다. 방향키로 조기 종료했으면 이 추정은 성립하지 않는다. 당시 종료 방법은 아직 확인되지 않았다. 학습의 `num_workers`는 데이터 로딩 설정으로, 이번 녹화 이미지 저장 워커와 별개다.

새 팔에 연결된 두 카메라의 동시 직접 읽기 결과:

| 카메라 | 읽은 프레임 | 경과 시간 | 실측 캡처 FPS |
| --- | --- | --- | --- |
| front | 60 | 2.0초 | 30.0 |
| wrist | 60 | 1.992초 | 30.12 |

이는 약 2초의 카메라 단독 입력 시험이다. 모터 통신·Rerun 표시·PNG 저장을 함께 하는 녹화 루프의 실측 FPS는 아니다. 새 [시험 녹화 블록](LEFT_RERECORD.md#3-시험-녹화-3개--프레임-속도와-새-시나리오-확인)은 30초 타이머로 종료한 뒤 저장 프레임 수를 확인하고 실행 로그를 보관한다.

## 교체한 리더·팔로워

| 역할 | 현재 장치 | 응답 ID | 최대 hardware_error | 온도 |
| --- | --- | --- | --- | --- |
| follower | `/dev/ttyACM1` | 11, 12, 13, 14, 15, 16 | 0 | 24~36°C |
| leader | `/dev/ttyACM0` | 1, 2, 3, 4, 5, 6 | 0 | 23~24°C |

- 리더 고정 경로: `/dev/serial/by-id/usb-ROBOTIS_OpenRB-150_E743255D50323952582E3120FF07301D-if00`
- 팔로워 고정 경로: `/dev/serial/by-id/usb-ROBOTIS_OpenRB-150_1B8E02E050323952582E3120FF071F2E-if00`
- 리더 1~5는 모델 1200, 6은 1190. 팔로워 11~13은 1060, 14~16은 1200으로 기존 코드의 모델 배치와 일치했다.
- Drive Mode와 Homing Offset은 기존 프로필 값과 일치했다. 기존 보정 파일은 2026-09-30 파일이므로, 파일 존재만으로 새 팔의 물리적 대기 자세·회전 방향까지 확인된 것은 아니다.
- 현재 토크는 읽기 시점에 모두 0이었다. 전압은 리더 4.6V, 팔로워 11~13이 11.7~11.8V, 14~16이 6.0V였다. 이번 읽기에서 오류가 없었다는 결과이며 장시간 전원 안정성을 보증하지 않는다.
- `/etc/udev/rules.d/99-omx.rules`는 이전 두 팔의 일련번호를 가리켜 `/dev/omx_*` 별칭이 생성되지 않았다. 시스템 파일을 수정하는 대신 문서의 실행 포트를 새 by-id 경로로 바꿨다.

다음 순서는 새 팔의 원격조종 확인 → 30초 시험 녹화와 실제 FPS 확인 → 왼쪽 v2 60개 신규 수집이다. 로봇 구동은 사용자가 터미널 명령으로 수행한다.
