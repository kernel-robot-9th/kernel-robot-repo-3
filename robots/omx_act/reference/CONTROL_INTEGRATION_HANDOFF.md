# OMX ACT 하역 — 관제 통합 인계

갱신: 2026-10-20. **관제 통합 세션은 이 문서를 먼저 읽는다.** 현재 결정은 추가 학습 대신 왼쪽 v2 5만 스텝 모델과 집기 쉬운 배치로 시연을 마무리하고, 관제에서 시작·완료 판정·중지를 연결하는 것이다. **오른쪽 v2는 3만·4만·5만·6만·7만 모델 준비를 완료했고 실제 평가 후 최종 체크포인트를 선택한다.**

## 1. 이번 시연의 확정 범위

- 핑키가 한 손님의 물건 3개를 싣고 정해진 위치에 주차한다.
- 주문의 목적지로 지정된 한 바구니에 모두 담는다. 물건 종류에 따른 좌우 분류는 없다.
- 우선 사용할 모델은 **왼쪽 ACT v2 5만 스텝**이다. 사용자 시험에서 10만보다 성공률이 좋았다는 판단에 따른 선택이며, 정량 성공률은 아직 기록하지 않았다.
- 성공하는 물건·위치·간격을 사용하고 주차 위치, 카메라, 바구니, 시작 자세를 고정한다. 임의 배치 전반의 성능을 보장하는 시연으로 설명하지 않는다.
- 추가 수집·재학습·왼쪽 체크포인트 재탐색은 이번 통합의 선행 작업으로 요구하지 않는다. 제안만 했던 `--policy.n_action_steps=20` 비교 시험도 적용하지 않는다.
- 오른쪽 데이터셋 v2는 로컬 60에피소드·28,962프레임 저장을 확인했다. **오른쪽 v2의 3만~7만 모델 5개를 검증·정리했으며 최종 선택과 실제 성능은 아직 미확정이다.** 우선 평가값은 5만이며 [RIGHT_V2_EVAL.md](RIGHT_V2_EVAL.md)의 전체 명령을 사용한다. 왼쪽 모델을 오른쪽 작업에 사용하지 않는다.

## 2. 현재 동작과 후속 구현을 구분할 것

| 항목 | 현재 상태 |
| --- | --- |
| ACT 실제 팔 실행 | 사용자가 평가 실행함. 물건 하나를 옮기는 동작이 가능하지만 헛집기도 발생 |
| 왼쪽 v2 모델 | 5만·10만의 파일과 설정 검증 완료. 시연에는 5만 선택 |
| 오른쪽 v2 모델 | 3만·4만·5만·6만·7만의 파일과 설정 검증 완료. 실제 평가·최종 선택은 미완료 |
| 연속 실행 | 30초씩 3회 대신 한 에피소드 최대 180초로 실행했을 때 사용자가 중간 끊김이 사라졌다고 확인 |
| 작업 완료 후 정지 | 미구현. 카트가 비어도 허공 집기·내리기를 반복할 수 있음 |
| 물건 위치에 대한 반응 | 사용자가 비슷한 위치의 허공을 집는 현상을 보고함. 원인은 확정하지 않음 |
| 관제 시작·중지 API, ROS 토픽 | 이 저장소에는 구현되어 있지 않음 |
| 카메라 기반 빈 카트·완료 판정 | 후속 관제 세션에서 구현할 요구사항 |
| 정지 확인 후 핑키 출발 연동 | 후속 관제 세션에서 구현할 요구사항 |

기존 3회 × 30초 명령은 시간에 따른 평가 반복이다. 한 물건의 성공이나 세 물건 하역을 감지하는 명령이 아니다. 30초마다 저장·인코딩과 정책 초기화가 있어 동작이 중간에 끊겼다. 연속 180초 명령도 **최대 실행 시간을 늘린 시험 명령일 뿐 자동 완료 기능은 없다.**

## 4. 실제 장치와 카메라

리더·팔로워를 모두 교체했다. 예전 `/dev/omx_follower`, `/dev/omx_leader` 별칭은 이전 USB 일련번호용 규칙이므로 사용하지 않고 아래 by-id를 사용한다. `/dev/ttyACM*`, `/dev/video*` 번호는 재연결 때 달라질 수 있다.

| 리더 | `/dev/serial/by-id/usb-ROBOTIS_OpenRB-150_E743255D50323952582E3120FF07301D-if00` |
| 팔로워 ID | `omx_follower_arm` |

| wrist | `/dev/v4l/by-id/usb-Innomaker_Innomaker-U20CAM-720P_SN0001-video-index0` |
| 두 카메라 설정 | OpenCV / MJPG / 640×480 / 30 FPS |

추론 실행에는 리더가 필요 없다. 기존 팔로워 보정 파일은 `/home/team2/.cache/huggingface/lerobot/calibration/robots/omx_follower/omx_follower_arm.json`이다. 다른 PC에서 같은 로봇을 구동할 때 이 보정 파일도 별도로 준비한다.

**카메라는 한 프로세스가 열고 프레임을 공유하는 방식으로 연결할 것을 권장한다.** 현재 LeRobot가 두 카메라를 사용한다. 관제 인식기가 같은 장치를 별도로 열도록 바로 붙이지 말고, 로봇 실행부가 받은 `front` 영상을 관제로 전달하는 연결을 먼저 만든다. 전달 방식은 관제 프로젝트의 기존 통신 구조에 맞춘다. 이 공유 기능은 아직 구현되어 있지 않다.

Rerun에서 `front`만 보였던 문제는 과거 뷰 배치 문제였고, 사용자가 두 화면이 보이는 것을 확인했다. 화면 칸이 없다는 이유만으로 추론의 `wrist` 입력도 없다고 판단하지 않는다. 카메라 구도 복원 명령과 v2 기준 이미지는 [LEFT_V2_EVAL.md](LEFT_V2_EVAL.md)에 있다.

## 5. 관제에서 이어 구현할 처리 순서

1. 핑키 주차 완료와 목적지를 확인하고 방향에 맞는 모델을 선택한다. 왼쪽은 v2 5만으로 선택했고 오른쪽은 실제 평가 후 선택해야 한다. 오른쪽 시험의 기본 5만을 최종 확정값으로 취급하지 않는다.
2. 준비된 배치와 대기 자세에서 하역 실행을 시작하고 관제 상태를 실행 중으로 바꾼다.
3. ACT 실행부의 `front` 영상으로 카트 안 물건 잔존 여부를 확인한다.
4. 빈 카트가 안정적으로 관찰되고 마지막 물건 내려놓기와 대기 자세 복귀까지 끝났는지 확인한다.
5. ACT 실행부에 중지를 요청하고 **추가 정책 동작 명령 전송이 중지됐다는 응답**을 기다린다.
6. 실제 중지 확인 후 하역 완료를 표시하고 핑키 출발을 허용한다.

통신 방식·API 경로·ROS 토픽명은 아직 정하지 않았다. 관제 저장소의 방식을 따르며, 다음 의미를 전달하면 된다.

| 방향 | 전달할 의미 |
| --- | --- |
| 관제 → 실행부 | 작업 식별자와 목적지를 포함한 시작 요청, 실행 중인 작업의 중지 요청 |
| 실행부 → 관제 | 준비·실행 중·실제 중지·오류 상태, 완료 판정에 사용할 영상과 팔 상태 |
| 관제 내부 | 마지막 담기 확인, 빈 카트 판정, 작업 완료·실패 사유 |

모델이 정상 종료 코드로 끝났거나 180초가 지났다는 사실만으로 하역 성공을 표시하지 않는다. 물건이 남거나 마지막 담기가 미확인인 상태는 완료가 아니다.

### 완료 판정에서 빠뜨리지 말 것

- **마지막 물건을 집어 올린 순간에도 카트는 빈다.** 빈 카트만 보고 멈추면 운반 중 중지될 수 있다.
- 팔·그리퍼·사람 손이 물건을 가리는 프레임은 빈 카트 증거로 사용하지 않는다. 화면에서 카트 영역이 충분히 보이는지도 확인한다.
- 빈 상태의 연속 확인 시간은 초기 권장 1~2초이며 실제 영상으로 조정한다. 카트 영역, 인식 방식, 대기 자세 관절값과 허용 오차는 아직 측정·구현하지 않았다.
- 마지막 물건이 지정 바구니에 내려놓였는지와 대기 자세 복귀를 함께 확인한다. 바닥이나 바구니 밖에 떨어진 경우를 하역 성공으로 세지 않는다.
- 관제의 화면 상태만 완료로 바꾸지 않는다. 실제 동작 전송 중지 확인까지 연결한다.

### 중지와 팔 자세 유지의 차이

현재 `lerobot-record`는 종료 시 `robot.disconnect()`를 호출하고, OMX 설정의 `disable_torque_on_disconnect` 기본값은 `true`다. **프로세스 종료가 대기 자세를 토크로 유지하는 기능과 같지 않다.** 마지막 목표로 이동이 남아 있을 수도 있으므로 중지 요청 수신만으로 정지 완료 응답을 보내지 않는다.

관제 통합 실행부에서 대기 자세 복귀·추가 정책 명령 중지·팔 자세 유지·연결 종료 순서를 구분한다. 기존 CLI를 강제 종료하는 것만으로 완료·정지 연동이 끝났다고 처리하지 않는다. 필요한 정지/유지 처리는 다음 세션의 구현 범위이며 이번 문서 갱신에서 로봇 설정을 바꾸지는 않았다.

## 6. 다음 세션에서 볼 소스 위치

아래는 문서 저장소가 아니라 **노트북의 별도 LeRobot 소스** 기준이다. 이 저장소에는 전체 LeRobot 소스가 없으므로 고정 커밋과 패치를 함께 사용한다.

| 파일 | 확인할 부분 |
| --- | --- |
| `src/lerobot/scripts/lerobot_record.py` | `record_loop`: 관측 → 전처리 → 정책 예측 → 동작 전송. 실행 중지 확인과 영상 공유 연결 위치 |
| 같은 파일의 `record` | 에피소드 시간 제한·저장·최종 종료 처리. 현재 외부 관제 API는 없음 |
| `src/lerobot/robots/omx_follower/omx_follower.py` | `get_observation`, `send_action`, `disconnect`, 손목 초기 목표 위치 패치 |
| `src/lerobot/robots/omx_follower/config_omx_follower.py` | 카메라 설정과 `disable_torque_on_disconnect` |
| `src/lerobot/policies/act/modeling_act.py` | `select_action`의 동작 큐와 `reset`. 다음 작업 시작 시 이전 작업의 큐를 이어 쓰지 않도록 초기화 |
| `src/lerobot/utils/control_utils.py` | 현재 CLI 키보드 이벤트. `Esc`는 수동 종료용이며 외부 관제 중지 API가 아님 |

ACT는 현재 한 번 예측한 100개 동작을 큐에서 실행한 뒤 새 예측을 한다. 관제 중지는 큐를 모두 소진할 때까지 기다리는 방식이 아니라 실행 루프에서 별도로 처리해야 한다. `n_action_steps=20`은 설명과 시험 제안만 있었고 실제 적용한 설정이 아니다.
