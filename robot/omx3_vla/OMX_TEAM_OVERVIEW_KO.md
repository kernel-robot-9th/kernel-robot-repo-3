# OMX 담당 PC 협업용 프로젝트 개요

작성 기준: 2026-10-17, 현재 프로젝트 소스 및 인계 문서 확인.
이 문서는 OMX 담당 PC의 개발자 또는 AI 코딩 에이전트에게 함께 전달한다.
구현 상태는 코드 기준이며, 실물 여러 대의 통합 동작 성공을 의미하지 않는다.

## 1. 프로젝트 목표와 전체 흐름

Pinky Pro 2대와 OpenMANIPULATOR(OMX) 3대를 이용한 상품 쇼핑·운반 시스템이다.
관제 PC가 주문과 작업 순서를 관리하고, OMX가 상품을 적재하거나 하역하며,
핑키가 뒤에 연결된 카트로 상품을 운반한다. 관제 PC의 Gazebo에는 실물의 측정
상태를 반영하여 전체 배치를 보여준다.

목표 작업 흐름:

1. 관제가 주문과 개별 상품 목록을 생성한다.
2. 핑키를 해당 상품 스테이션으로 이동시키고 도킹·정지를 확인한다.
3. OMX1 또는 OMX2가 상품을 카트에 적재하고 결과를 보고한다.
4. 핑키가 OMX3 하역 스테이션으로 이동하고 도킹·정지한다.
5. OMX3가 상품을 지정 바구니에 옮긴 뒤 실제 투입 및 팔 안전 복귀를 확인한다.
6. 관제가 완료를 기록하고 핑키 출발을 허가한다.

상품 역할의 현재 설계는 OMX1 8종, OMX2 1종, OMX3 통합 하역이다.
9종 전체의 SKU·치수·집기 방식과 OMX1·2 적재 절차는 담당자 간 확정이 필요하다.
OMX3 인계 요청은 주문당 1~4개 상품을 지원한다.

## 2. 장치별 책임

| 장치 | 담당 범위 |
|---|---|
| 관제 PC(이 프로젝트) | 주문·작업 관리, 요청/상태 연동, Gazebo, 실물 상태 표시, 관제 화면 |
| OMX1 PC | OMX1 USB·드라이버 소유, 상품 집기·카트 적재, 측정 관절 상태와 작업 결과 발행 |
| OMX2 PC | OMX2 USB·드라이버 소유, 상품 집기·카트 적재, 측정 관절 상태와 작업 결과 발행 |
| OMX3 PC | OMX3 USB·드라이버 소유, 시연 수집·학습/정책 실행 연동, 카트에서 바구니로 하역, 결과 발행 |
| Pinky1·2 내장 PC | 각 로봇 bringup, 센서·주행·정지 처리, 위치 및 도킹 상태 제공 |

실물 모터 명령은 해당 로봇의 제어기가 수행한다. 관제와 Gazebo는 측정 상태를
받는다. USB를 제조사 제어기와 별도 SDK 읽기 노드가 동시에 열지 않는다.
OMX3 시연 수집과 학습은 다른 PC에서 수행하며 이 관제 PC에서 시작하지 않는다.

## 3. 구현된 범위와 남은 작업

| 항목 | 현재 상태 |
|---|---|
| 제조사 모델 5대의 동일 Gazebo 실행 | 구현됨. 로봇별 시뮬레이션 제어 인터페이스 분리 |
| 맵·카트·선반·쟁반·바구니 | 구현됨 |
| OMX2 실물 관절 표시 | USB 읽기 또는 외부 JointState 토픽 입력 구현 |
| OMX3 실물 관절 표시 | `omx3_mode:=mirror` 및 외부 JointState 입력 구현 |
| Pinky1 실물 위치 표시 | 오도메트리 기반 구현. 카메라 위치 보정 코드도 있음 |
| OMX3 인계 관리 | 요청 검증, 중복 방지, 상태 전이, 완료 조건, 통신 단절 관리 구현 |
| OMX3 실물 실행기·도킹 센서·투입 성공 판정 | 상대 PC 및 실제 센서와 연동 필요 |
| OMX1 실물 표시·Pinky2 실물 표시 | 현재 launch의 관찰 옵션 일반화 필요 |
| OMX1·2 실물 적재 작업 통신 | 공통 규격과 실행기 구현 필요 |
| 5대 실물 자동 주문 수행 | 미완성. 실제 다중 PC 통신과 통합 검증 필요 |

기존 `FOUR_COMPUTER_PLAN_KO.md`의 “관찰 옵션은 OMX2/Pinky1만 구현” 설명은
초기 계획 시점의 기록이다. OMX3는 이후 추가된
`OMX3_HANDOVER_INTERFACE_KO.md` 및 현재 launch를 기준으로 한다.
과거 로그의 검사 통과 기록은 이번 문서 작성 중 새로 실행한 결과가 아니다.

## 4. 네트워크와 공통 상태 규격

관제 PC, OMX PC 3대, 핑키 2대를 같은 공유기 네트워크에 연결한다.
ROS_DOMAIN_ID, DDS/RMW 설정, 방화벽과 discovery 도달 여부를 함께 확인한다.
도메인 0과 1을 사용한 과거 단독 시험 기록이 섞여 있으므로 각 PC의 실제 실행값을
확인한 뒤 통합 값을 합의한다. 아래 예시는 도메인 0이다.

| 로봇 | 실물 상태 토픽 | 적용 상태 |
|---|---|---|
| OMX1 | `/real/omx1/joint_states` | 협업 목표 이름 |
| OMX2 | `/real/omx2/joint_states` | 현재 관찰 입력 지원 |
| OMX3 | `/real/omx3/joint_states` | 현재 관찰 입력 지원 |
| Pinky1·2 | `/real/pinky1/odom`, `/real/pinky2/odom` | 분산 구성 목표 이름. 실제 bringup remap 필요 |

OMX 메시지는 `sensor_msgs/msg/JointState`로 발행한다.

- `name`: `joint1`, `joint2`, `joint3`, `joint4`, `joint5`, `gripper_joint_1`.
- `position`: 이름에 대응하는 제조사 URDF 기준 관절 위치. 팔은 rad,
  그리퍼도 현재 URDF의 관절 정의에 맞춘 값으로 변환한다.
- 측정 시각을 포함하고 목표 20Hz로 발행한다. 목표 명령 대신 실제 측정값을 보낸다.
- LeRobot 정규화 값이나 모터 tick을 그대로 전송하지 않는다.
- 로봇별 상태 토픽의 발행자는 하나로 유지한다.

현재 OMX 관찰 노드는 0.5초 이상 유효 입력이 없거나 발행자가 정확히 하나가 아니면
표시 갱신을 중단한다. 이것이 실물 모터 정지를 뜻하지는 않는다.
실물 노드는 실제 시간을 사용하고 시뮬레이션 `/clock` 적용 범위를 분리한다.
`GZ_IP=127.0.0.1`은 관제 PC 내부 Gazebo 통신 설정이다.

## 5. OMX3 담당 PC가 구현할 인계 규격

정확한 필드·검증 조건은 [OMX3 인계 규격](OMX3_HANDOVER_INTERFACE_KO.md)을 따른다.
아래 모든 요청/상태/중단 메시지는 `std_msgs/msg/String`의 JSON이다.

| 방향 | 토픽 | 의미 |
|---|---|---|
| 관제 → OMX3 PC | `/real/omx3/handover/request` | 요청 ID, 주문 ID, 핑키 ID, 개별 물체 목록, 목표 바구니 |
| OMX3 PC → 관제 | `/real/omx3/handover/status` | accepted/running/completed/failed, 누적 완료 물체 ID |
| 관제 → OMX3 PC | `/real/omx3/handover/stop` | 요청 ID와 중단 사유 |

핑키1은 맵의 왼쪽 바구니, 핑키2는 오른쪽 바구니를 사용한다.
같은 SKU 여러 개도 `object_id`는 각각 달라야 한다. OMX3는 한 번에 한 인계만 수행한다.
상대 실행기는 요청 ID로 중복 실행을 방지하고 실제 도킹·정지를 재확인한다.

작업 중 상태를 1Hz 이상 보내는 것을 권장한다. 완료 보고에는 요청의 모든
`placed_object_ids`, `placement_verified=true`, `arm_safe=true`가 필요하다.
실제 투입과 안전 복귀를 확인한 뒤에만 이 값을 보낸다.
관제의 `release_pinky`는 출발 허가 상태이며 자체적으로 핑키를 주행시키지 않는다.

기본 10초 동안 유효 상태가 없으면 관제는 communication_lost로 고정한다.
OMX3 PC는 stop 처리와 자체 통신 watchdog을 구현해야 한다.
실제 네트워크 단절 상태에서는 관제 stop 토픽의 도착을 전제할 수 없다.

OMX1·2의 적재 요청에 이 프로토콜을 그대로 사용한다고 가정하지 않는다.
적재 규격에는 상품 출발 위치, 카트 적재 위치, 성공 판정과 안전 복귀 조건을
정의하고 관제와 합의한 뒤 구현한다.

## 6. 배치와 관측 한계

맵은 2.0×1.5m이며 좌표 단위는 m이다. 선반 위 OMX 베이스는
OMX1 `(0.305, 1.32, 0.11)`, OMX2 `(0.90, 1.32, 0.11)`,
OMX3 `(1.60, 1.32, 0.11)`이며 기본 yaw는 −π/2다.
OMX3 바구니 중심은 왼쪽 `(1.29, 1.32, 0)`, 오른쪽 `(1.91, 1.32, 0)`이다.
이 좌표는 Gazebo 배치 기준이며 실제 설치·도킹 위치와 대조해야 한다.

카트 적재판은 12.5×15.4cm다. 최대 4개 상품의 분리 배치와 집게 접근 공간은
실물 치수로 확인해야 한다. 관절 동기화만으로 상품 위치·집기·투입은 동기화되지 않는다.
현재 진라면 영상 시험은 OMX2 오른쪽 쟁반의 제한된 관측 조건을 지원한다.
카트 이동·공중 자세·그리퍼 부착·낙하를 일반적으로 추적하는 기능은 없다.

## 7. 통합 순서와 담당 PC 회신 항목

1. 각 PC의 OS, ROS 버전, RMW, 도메인, IP, 로봇 모델과 USB 소유 제어기를 공유한다.
2. OMX별 관절 이름·순서·영점·부호·단위를 확인하고 측정 JointState를 송수신한다.
3. 관제에서 OMX2/3 표시와 지연·입력 단절 동작을 검증한다. OMX1 표시를 확장한다.
4. OMX3 요청/상태/중단을 모의 실행기로 왕복 검증한다.
5. 실제 도킹 확인과 상품 한 개 하역·투입 판정을 연결한다.
6. OMX1·2 적재 규격을 확정하고 핑키1 + OMX2 + OMX3의 한 상품 흐름을 검증한다.
7. 핑키2·OMX1, 여러 상품·중복 SKU, 스테이션 점유 및 실패 복구를 추가한다.

각 OMX 담당자는 다음을 회신한다: 현재 실행 명령, 발행/구독 토픽과 타입,
관절 변환 규칙, 상태 발행 주기, 작업 성공 판정 방법, 중단/연결 단절 시 동작,
구현된 범위와 관제 측에 필요한 변경. 관제 공용 launch·맵 변경은 변경 내용을
공유하고 통합하며 로봇별 드라이버/실행기는 해당 PC에서 관리한다.

## 8. 다른 PC의 AI에게 전달할 시작 문장

> 이 PC는 상품 쇼핑 로봇 프로젝트의 OMX 담당 PC입니다. 함께 전달한
> `docs/OMX_TEAM_OVERVIEW_KO.md`를 먼저 읽고, OMX3 담당이라면
> `docs/OMX3_HANDOVER_INTERFACE_KO.md`와 `docs/OMX3_IMITATION_LEARNING_KO.md`도
> 읽어 주세요. 관제 PC는 주문·상태 관리와 Gazebo 표시를 담당하고 각 OMX PC가
> 실물 USB와 제어기를 소유합니다. 먼저 이 PC가 OMX1/2/3 중 무엇을 맡는지와
> 현재 드라이버·관절 단위·ROS 토픽을 확인해 구현 상태를 정리해 주세요.
> 관제에 측정 JointState를 제공하고 위 통합 순서에 맞춰 연동합니다.
> 이미 구현된 관찰 기능과 앞으로 구현할 실물 자동 작업을 구분해 주세요.
